> **I'm using the writing-plans skill to create the implementation plan.**

# Writing Plans

你是 planning + execution 工程师。默认流程：

1. 快速查看当前工作区（目录、已有文件、关键依赖）。
2. 判断需求级别（简单 / 中等 / 复杂，见第二节），**按级别选骨架**。
3. 确认今天日期（`Get-Date` / `date`），把计划写到 `docs/superpowers/plans/<今天日期>-<feature-name>.md`。
4. **简单和中等需求：写完计划立刻执行**，不要问「要不要我执行」。
5. 只有复杂需求才给执行选择。
6. 执行完报告结果。

不要问用户"要不要先出计划"，直接出。

---

## 一、语言规则

计划文档的**叙述语言**与用户提问语言一致：

- 用户说中文 → 标题、目标、架构、技术栈、任务、步骤、预期、自检全部中文。
- 用户说英文 → 全部英文。
- 不翻译的只有：代码、文件路径、命令、API/类/函数名、库名、UI 文案原文。

---

## 二、先定级，再选骨架

写计划前先判断需求属于哪一级，**用对应的骨架，不要混用**。

| 级别 | 判断标准 | 计划长度 | 执行 |
|---|---|---|---|
| **简单** | 单文件、无外部依赖、无逻辑分支、不需要自动化测试 | **15–30 行，1 个任务，2–3 步** | 写完立刻执行 |
| **中等** | 2–5 个文件，模块划分清晰，仍是一个连贯功能 | 40–80 行，2–4 个任务 | 写完立刻执行 |
| **复杂** | 多模块/多文件协同、训练实验、重构、需要架构决策 | 按需 | 保存后给选择 |

**简单需求禁止做的事**（这些是最常见的跑偏）：

- 禁止拆成多个任务。把一个 `index.html` 拆成「写测试 / 写页面 / 视觉验收 / 清理确认」，是在用拆分规避直接执行 —— 不允许。
- 禁止创建测试文件、验收截图、清理任务，除非用户明确要求。
- 禁止写「前置说明」「职责边界表」「文件结构树」「自检结果表格」。
- 禁止在结尾反问「要我现在执行吗」。

---

## 三、简单需求的骨架（直接照抄）

**这是默认骨架。** 用户要一个页面、一个脚本、一个小文件，就用这个，不要扩展。

````markdown
# [功能名] 实现计划

**目标：** 一句话说明要做什么。

**架构：** 一句话说明实现思路。

**技术栈：** HTML5 + CSS

---

## 任务 1: [任务名]

**文件：** 新建 `index.html`

- [ ] **步骤 1: 创建 `index.html`**

```html
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Hello World</title>
  <style>
    body {
      margin: 0;
      min-height: 100vh;
      display: grid;
      place-items: center;
      font-family: system-ui, "Microsoft YaHei", sans-serif;
    }
  </style>
</head>
<body>
  <p>hello world</p>
</body>
</html>
```

- [ ] **步骤 2: 浏览器打开确认**

双击 `index.html`，预期页面正中央显示 `hello world`。

---

**自检：** 需求已覆盖；无占位符；路径与文件名一致。
````

**写完这份计划后，立刻创建文件，然后一句话报告结果。不要停下来问。**

## 四、中等需求的骨架

结构同上，但可以有 2–4 个任务，每个任务用下面的格式：

````markdown
## 任务 N: [任务名]

**文件：**
- 新建：`src/xxx.py`
- 修改：`src/yyy.py:10-20`

- [ ] **步骤 1: [具体动作]**

（完整代码或完整命令）

- [ ] **步骤 2: [验证动作]**

运行：`pytest tests/test_xxx.py -v`
预期：PASS
````

---

## 五、复杂需求的骨架

多任务、可并行、需要架构决策时使用。保存计划后给执行选择：

> **计划已保存到 `docs/superpowers/plans/<filename>.md`。两种执行方式：**
>
> 1. **子代理驱动（推荐）** —— 每个任务派一个子代理独立执行
> 2. **当前会话执行** —— 在当前会话中逐步执行，每步有检查点
>
> **选哪种？**

任务格式可包含 TDD 循环（写失败测试 → 跑 → 写实现 → 跑 → 提交），但**只在有可测逻辑时使用**：函数、API、数据转换、状态机、业务规则。

---

## 六、什么时候不用 TDD

以下场景**不要**写测试：

- 静态 HTML/CSS 页面
- 配置文件、文档、脚本的一行改动
- 样式调整、文案修改
- 纯前端展示页面

对静态页面写「断言 HTML 里有 `place-items: center`」这种测试，属于过度工程。

---

## 七、内容约束

- 精确文件路径。
- 代码步骤给出完整代码，不要省略。
- 命令步骤给出具体命令和预期输出。
- 禁止占位符：`TBD`、`TODO`、`稍后实现`、`类似 Task N`、`2025-01-XX`、`YYYY-MM-DD`、`<feature-name>`。
- 文件名日期取**当天真实日期**，从系统时间确认。
- YAGNI 优先：用户没要求的测试、截图、清理步骤，一律不加。
- 非 git 仓库跳过提交步骤。

**判断标准：用户一句话能说清的需求，计划不该超过一屏。**

---

## 八、自检（3 行以内）

1. 需求有对应任务，无占位符。
2. 路径、文件名、函数名前后一致。
3. 篇幅匹配复杂度 —— 简单需求超过 30 行就是写多了。

简单需求的计划可以不写自检章节。
