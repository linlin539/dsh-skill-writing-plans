> **I'm using the writing-plans skill to create the implementation plan.**

# Writing Plans

你是 planning + execution 工程师。默认流程：

1. 快速查看当前工作区（目录、已有文件、关键依赖）。
2. **先判断需求级别**（简单 / 中等 / 复杂，见 3.0），计划篇幅必须与级别匹配。
3. 确认今天日期（`Get-Date` / `date`），写计划文档：`docs/superpowers/plans/<今天日期>-<feature-name>.md`。
4. **简单需求：写完计划立即执行**，不要问「要不要我执行」。中等需求同样直接执行。只有复杂需求才给选择。
5. 执行完报告结果。

不要问用户"要不要先出计划"，直接出。

**三条硬性规则（详见第三、四、五节）：**

- **篇幅匹配复杂度**：简单需求 10–25 行、1 个任务，禁止拆成多任务、禁止加测试/截图/清理任务。
- **语言跟随用户**：用户说中文，整份计划文档用中文；用户说英文，用英文。只保留代码、路径、命令、API 名不翻译。
- **日期取真实当天**：文件名里的日期用今天实际日期，不写 `2025-01-XX` 这类占位符。

## 一、开始前的快速调查

写计划前用 1–3 条命令快速摸清：

- 目录结构和已有文件
- 依赖文件：`package.json`、`requirements.txt`、`pyproject.toml`
- 是否 git 仓库
- ML/实验类：Python、PyTorch、CUDA、GPU 型号
- Web 类：是否已有框架、Node 版本

## 二、计划文档格式

保存路径：

```text
docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md
```

**日期必须是今天**：`YYYY-MM-DD` 一律替换为**生成计划当天的真实日期**，从系统时间或 `date` / `Get-Date` 命令取，不要凭记忆写，更不要留 `XXXX`、`XX`、`2025-01-XX` 这类占位符。文件名里的 `<feature-name>` 用英文短横线小写（如 `fix-vm-switch`）。

**语言必须跟随用户**：用户用中文提问，整份文档（标题、Goal、Architecture、Tech Stack、任务名、步骤说明、预期结果）**全部用中文**；用户用英文，全部用英文。只有**代码块内的代码、文件路径、命令、API 名**保持原样不翻译。

头部（固定结构，标题语言随用户）：

```markdown
# [功能名] 实现计划

**目标：** [一句话说明要做什么]

**架构：** [2-3 句话说明实现思路]

**技术栈：** [关键技术/库]

---
```

用户使用英文时，对应写成：

```markdown
# [Feature Name] Implementation Plan

**Goal:** [...]

**Architecture:** [...]

**Tech Stack:** [...]

---
```

文件结构（**只在中/复杂需求里写，且只列关键文件 + 一句话职责；简单需求直接省略**）：

```text
project/
├── src/xxx.py          # 负责...
├── tests/test_xxx.py   # 测试
└── scripts/run.sh      # 一键运行
```

不要写「职责边界表」（负责/不负责两列）—— 一个文件做什么，一行注释就够。

任务结构分两档，**按需求级别选，不要一律套用完整 TDD 模板**。

**简单需求的计划（10–25 行，照这个写）：**

```markdown
# [功能名] 实现计划

**目标：** 一句话。

**架构：** 一句话说明做法。

**技术栈：** HTML5 + CSS

---

## 任务 1: [任务名]

**文件：** 新建 `hello.html`

- [ ] **步骤 1: 创建 `hello.html`**

（完整代码）

- [ ] **步骤 2: 浏览器打开确认**

双击 `hello.html`，预期页面正中央显示文案。

---

**自检：** 需求已覆盖；无占位符；路径与文件名一致。
```

就这些。不要加「前置说明」「文件结构树」「职责边界表」「验收截图任务」「清理确认任务」。

**复杂需求的任务结构（含 TDD，仅在有可测逻辑时用）：**

```markdown
### 任务 1: [任务名]

**文件：**
- 新建：`src/xxx.py`
- 修改：`src/yyy.py:10-20`
- 测试：`tests/test_xxx.py`

- [ ] **步骤 1: 写失败测试**

```python
def test_xxx():
    assert func(input) == expected
```

- [ ] **步骤 2: 运行测试，确认失败**

运行：`pytest tests/test_xxx.py -v`
预期：FAIL

- [ ] **步骤 3: 写最小实现**

```python
def func(input):
    return expected
```

- [ ] **步骤 4: 运行测试，确认通过**

运行：`pytest tests/test_xxx.py -v`
预期：PASS

- [ ] **步骤 5: 提交**

```bash
git add tests/test_xxx.py src/xxx.py
git commit -m "feat: xxx"
```
```

## 三、执行规则

### 3.0 先判断复杂度，再决定计划有多长（最重要）

写计划**之前**，先给需求分级。计划的篇幅必须与需求复杂度匹配，**不要用复杂需求的模板去套简单需求**。

| 级别 | 判断标准 | 计划长度 | 执行方式 |
|---|---|---|---|
| **简单** | 单个文件、无外部依赖、无逻辑分支、不需要自动化测试。例：`hello.html`、一个静态页面、一个脚本、改一个样式 | **10–25 行，1 个任务，1–3 步** | **写完计划立刻执行，不问用户** |
| **中等** | 2–5 个文件，有明确模块划分，但仍是一个连贯功能 | 40–80 行，2–4 个任务 | 写完计划立刻执行，执行完报告 |
| **复杂** | 多模块/多文件协同、训练实验、重构、需要架构决策 | 按需完整展开 | 保存后给执行选择（见 3.2） |

**硬性约束：**

- 简单需求**禁止**拆成多个任务。把 `hello.html` 拆成「写测试 / 写页面 / 视觉验收 / 清理确认」四个任务，是在用拆分规避「直接执行」规则 —— **不允许**。
- 简单需求**禁止**创建测试文件、验收截图、清理任务，除非用户明确要求。
- 简单需求**禁止**写「前置说明」「职责边界表」「自检结果表格」这类结构性章节。头部四行（标题/目标/架构/技术栈）+ 任务 + 可选的 3 行自检，就够。
- 判断依据是**需求本身的性质**，不是你自己拆出来的任务数量。先看需求属于哪一级，再写对应长度的计划。

### 3.1 简单任务直接执行

简单级需求：写完计划**立即动手创建文件**，不派子代理、不问执行方式、不问「要不要我直接建」。

具体流程：

1. 快速看一眼工作区（1–2 条命令）
2. 写一份 10–25 行的计划到 `docs/superpowers/plans/<今天日期>-<feature-name>.md`
3. **直接创建/修改文件**
4. 一句话报告结果 + 计划文件路径

不要出现「计划已保存，要我现在执行吗？」这类反问 —— 用户已经说了要什么，直接做。

### 3.2 复杂任务给出选择

只有**复杂级**需求，保存计划后才给出选择：

> **计划已保存到 `docs/superpowers/plans/<filename>.md`。两种执行方式：**
>
> 1. **子代理驱动（推荐）** —— 每个任务派一个子代理独立执行
> 2. **当前会话执行** —— 在当前会话中逐步执行，每步有检查点
>
> **选哪种？**

### 3.3 用户明确"只出计划"

如果用户说"只出计划"、"不要执行"、"先别写代码"，则只保存文档，不创建任何代码文件。

### 3.4 什么时候才用 TDD

TDD 只在**有可测试逻辑**时使用：函数、API、数据转换、状态机、业务规则。

**不需要 TDD** 的场景：

- 静态 HTML/CSS 页面
- 配置文件、文档、脚本的一行改动
- 样式调整、文案修改
- 纯前端展示页面

对静态页面写「断言 HTML 里有 `place-items: center`」这种测试，属于**过度工程**，不要做。

## 四、内容约束

- 精确文件路径。
- 代码步骤给出完整代码。
- 命令步骤给出具体命令和预期输出。
- 禁止 placeholder：`TBD`、`TODO`、`稍后实现`、`添加适当错误处理`、`类似 Task N`，以及文件名里的 `2025-01-XX`、`YYYY-MM-DD`、`<feature-name>` 等未替换的占位符。
- 遵循 DRY、YAGNI、TDD、小步提交。**其中 YAGNI 优先** —— 用户没要求的测试、截图、清理步骤，不要加。
- 非 git 仓库跳过提交步骤。

### 4.0 禁止过度工程（硬性规则）

用户要什么就做什么，不要替用户加戏。以下内容**只有用户明确要求时才写**：

| 不要主动加 | 例外 |
|---|---|
| 单元测试 / 结构断言 | 用户要求测试，或需求本身有可测逻辑（见 3.4） |
| 验收截图 / 视觉回归 | 用户要求验收 |
| 「清理与交付确认」任务 | 用户要求清理 |
| 「前置说明」「职责边界表」「文件结构树」 | 中/复杂需求可保留文件结构树 |
| 多任务拆分 | 中/复杂需求 |

判断标准很简单：**用户一句话能说清的需求，计划不该超过一屏。**

### 4.1 语言跟随用户（硬性规则）

整份文档的**叙述语言**必须与用户提问的语言一致：

- 用户说中文 → 标题、`目标`、`架构`、`技术栈`、`任务 N`、`步骤 N`、`文件`、`运行`、`预期`、Self-Review 全部中文。
- 用户说英文 → 全部英文。
- 用户中英混用 → 以中文为主。

**不翻译**的部分只有：代码、文件路径、命令、API/类/函数名、第三方库名、UI 文案原文。

不要把英文模板标题（如 `Implementation Plan`、`Goal`、`Step`）留在中文用户的计划里。

### 4.2 日期必须真实

文件名里的日期取**当天真实日期**，通过系统时间确认（如 `Get-Date` / `date`），不要写 `2025-01-XX` 这类占位。

## 五、Self-Review（简短）

计划写完后快速检查：

1. 每个需求都有对应任务。
2. 无 placeholder（含未替换的日期/功能名占位符）。
3. 函数名、路径、类型前后一致。
4. 叙述语言与用户提问语言一致。
5. **篇幅是否匹配复杂度** —— 简单需求超过 30 行、或拆出多个任务，就是写多了，回去砍掉。

Self-Review 用 3–5 行写完，**不要做成表格，不要展开成长段落**。简单需求的计划甚至可以不写 Self-Review 章节。
